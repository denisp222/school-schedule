# Выпуск и автоматические обновления

## Один раз

Репозиторий публичный: клиент скачивает выпуски без GitHub-токенов.
Исходники и выпуски не содержат школьной базы.

1. `python tools/release_manifest.py --repository OWNER/REPOSITORY` создаёт
   локальный ключ в `.private/update-signing-key.txt` и записывает только
   открытый ключ и адрес репозитория в `app/update_channel.json`.
2. Сохраните значение закрытого ключа в GitHub Actions secret
   `UPDATE_SIGNING_KEY`. Не добавляйте файл ключа в Git, Issues или журналы.
   Сохраните отдельную защищённую копию ключа: замена ключа требует переходного
   выпуска со старой доверенной подписью.
3. В настройках репозитория включите неизменяемые выпуски (release immutability)
   и защиту основной ветки. Ограничьте доступ к Actions secrets.
4. Установите первую версию с поддержкой обновлений поверх прежней у пользователя.

## Обычный выпуск

Обновите `app/version.py`, `app/releases.py`, `CHANGELOG.md`, README и ключи
кэша интерфейса. Проверьте изменения и закоммитьте их локально. Затем выполните
`python tools/publish_source.py --release`. Скрипт экспортирует только текущие
проверенные исходники в отдельный репозиторий `build/public-source`, создаёт
публичный коммит с адресом `noreply`, отправляет основную ветку и тег `vX.Y.Z`.
Старая локальная история с личными метаданными автора не отправляется.
Workflow `Public Windows release` проверит историю Git, запустит тесты,
подготовит официальные зависимости, соберёт приложение с пустой базой,
проверит состав, подпишет описание и опубликует выпуск. При сбое загрузки
файлов выпуск останется черновиком, недоступным обновлению.

Исходники Actions закреплены на SHA; для установки Python-зависимостей
используется `requirements-lock.txt`. Право записи есть только у выпуска.
Не запускайте выпуск для непроверенного кода и не подключайте self-hosted
runner со школьными файлами. Обычные проверки PR не получают ключ подписи.

## На компьютере пользователя

Программа сначала открывает расписание. Подписанный `update.json` проверяется
в фоне, без блокировки запуска. В основном окне предлагаются «Позже» и
«Загрузить обновление». Даже после загрузки программа остаётся открытой:
установка начинается только по кнопке «Установить и перезапустить».
При отсутствии сети или ошибке текущая программа продолжает работать.
Незавершённая попытка не повторяется автоматически при следующем запуске.
Версию 2.22.0 нужно один раз установить вручную поверх старого обновлятора.

При запуске независимого установщика и следующего экземпляра очищаются
служебные переменные замороженного приложения и выставляется
`PYINSTALLER_RESET_ENVIRONMENT=1`, как требует
[документация PyInstaller](https://pyinstaller.org/en/stable/common-issues-and-pitfalls.html).
Проверка установщика воспроизводит унаследованное окружение старой сборки.
Проверяются подпись Ed25519, версия, доверенный адрес, размер и SHA-256.
Описание не может подменить репозиторий, произвольный URL или понизить версию.
Файл повторно проверяется непосредственно перед запуском установки.

После SQLite-backup старый процесс закрывается. Отдельный процесс запускает
установщик в прежнюю папку и открывает приложение после успешной установки.
Программа не требует удаления старой версии или прав администратора при
обычной пользовательской установке. Голосовой пакет, установленный ранее,
сохраняется при обновлении основного приложения; CI не скачивает его заново.
Новая публичная установка содержит основное приложение без голоса.

База и локальные шаблоны не перезаписываются. Одна резервная копия перед
обновлением находится в `Data/before-update/schedule.sqlite3`; она не содержит
копии ключа AI. Отдельные ключи остаются в пользовательской папке данных.
Установка не добавляет приложение в автозагрузку Windows.

Текущая подпись выпуска защищает подлинность файла для обновляющей программы;
она не является сертификатом Authenticode и не отменяет Windows SmartScreen.
Сбой или отключение питания во время работы установщика может потребовать
повторной установки. База остаётся отдельно и имеет резервную копию.
